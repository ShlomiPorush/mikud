## Product intent and boundaries

- **Problem:** see requirements section 1. One owner, about 30 projects, work happening in T3 agent threads.
- **Users:** the owner (desktop and phone) and his AI agents.
- **Stage:** preparation. Single launch after a dry run on real data and the owner's approval (requirements section 9).
- **Deployment shape:** one application container and a PostgreSQL database. Development and the dry run run on the owner's PC. The owner deploys production himself; agents never deploy.
- **Non-goals:** multiple users or roles, passkeys, OAuth for agents, backup codes (recovery is a command on the server), importing or syncing GitHub Issues, writing to T3 or to GitHub, a backup feature (the owner backs up the database with his own tools), public internet exposure, an offline mobile app, generic Kanban features (swimlanes, free drag and drop, due dates, assignees).

### Data model

Status: the schema exists in `src/server/db/schema.ts` (migration `drizzle/0000_initial.sql`); the services in `src/server/services/` write it. Choices made in the schema: codes are text columns with database checks; a project's current goal is its one goal that is not closed (a partial unique index), not a column on `projects`; the items of a project block its deletion (`ON DELETE RESTRICT`) until the services move them; thread links, comments, goals, proposals and security sources go with their parent; `closed_at` is set exactly when the status is `done` or `not_relevant`; `severity` is only on `security` items; `settings` is a single row; `visits` carry the browser (a `devices` row). Migration `0003_better-auth` adds the Better Auth tables and drops the device secret; `0004_auth-epoch` added the auth epoch. `0005_end-sessions` (a custom migration made with `drizzle-kit generate --custom`) ends every session once; `0006_auth-documented` drops the session clocks, the TOTP proof and the epoch, adds Better Auth's rate-limit table, the api-key plugin's table and the single-owner index; `0007_owner-settings` adds the owner's settings.

- `projects`: name, slug, T3 project id (unique, optional), GitHub repository `owner/name` (optional), stage (nullable until the owner sets one), current goal, where-we-are line, open Issues count with its as-of time.
- `goals`: project, text, created and closed time. Progress is the count of `done` items linked to the current goal out of all items linked to it.
- `items`: project (null for the inbox), type, status, title, body, severity (security only), goal, `version` (optimistic concurrency), status set by (actor kind) and when, created by, created, updated and closed time.
- `item_threads`: item, T3 thread id (unique), T3 project id, title, last T3 status and settled flag, last T3 activity time, linked time.
- `suppressions`: T3 thread ids and T3 project ids whose item or project the owner deleted; the sync never recreates them. Every transaction that creates, moves, links or deletes thread links, creates items or projects from the sync, deletes items or projects, or writes or removes suppressions takes one global transaction-level advisory lock as its first statement, so these run one at a time and never deadlock. The sync checks a suppression inside such a transaction, so a delete that commits during a run still wins. The owner can remove a suppression, or all of them, in the UI.
- `comments`: item, author, text, thread id, time.
- `stage_proposals`: project, proposed stage, reason, author, state (`open`, `accepted`, `rejected`).
- `security_sources`: project, family (`dependabot`, `code_scanning`, `secret_scanning`, `overview`), coverage (`enabled`, `not_enabled`, `no_access`, `error`, `unknown`), counts by severity, data as-of time (the source's last success, not the sync time).
- `sync_runs`: kind, start and end, outcome, counts, per-record errors.
- `job_runs`: job, local date, state (`sending`, `sent`, `failed`, `unknown`, `skipped`), time, detail (an error code), and for a sent morning message the time its "new since" ran to (`covers_until`: the start of its read minus the one-minute safety margin), where the next message starts counting. Unique on job and local date.
- `telegram_updates`: `update_id` (primary key), outcome (`item_created`, `ignored`, `refused`), time.
- `visits`: one row per owner visit, for "new since your last visit".
- `settings`: closed-item days in the overview (default 7), date and time format, language, the days a browser stays signed in without Mikud open (default 30), sign-in codes to Telegram (off by default), the Telegram bot token (encrypted with `MIKUD_SETTINGS_KEYS`) and chat id, and the private domains of the secret check. The morning time and days are fixed (plan review P19): they must stay after the reconciler's fixed T3 schedule.
- `devices`: browser identities for "new since your last visit", named by the `mikud_browser` cookie (label, created, last seen; `revoked` only on browsers ended before sign-in existed). Never a credential.
- `auth_user`, `auth_account`, `auth_session`, `auth_verification`, `auth_two_factor`, `auth_rate_limit`, `auth_api_key`: Better Auth's tables and those of its plugins, with its field names and nothing added. Only Better Auth writes them. A unique index on a constant (`auth_user_single_owner`) allows one owner.
- `audit`: time, actor kind and label, action, entity, before and after (JSON), source (`ui`, `api`, `mcp`, `telegram`, `sync`).

### Agent and sync rules

Status: implemented server-side in `src/server/services/threads.ts`, `sync.ts` and `sync-rules.ts`, with a test per rule. The sync tool on the PC that collects the snapshots is implemented in `src/sync/` (row 9).

- **Start of thread, one call.** MCP `mikud_start_thread(threadId, parentThreadId, projectId?, title, itemId?)` finds the item linked to the thread, or links the given item, or creates one, and sets `in_progress`, in one transaction. The unique thread id makes a retry or a race return the existing item instead of creating a second one.
- **Status from T3, decided per item over all its linked threads:** any linked thread `running` (or `starting`, `queued`, `preparing`) → `in_progress`; otherwise any `waiting` → `waiting_on_you`; otherwise all linked threads settled → `done`. A `completed` but unsettled thread changes nothing.
- **The owner wins.** The sync changes an item only when its status was last set by an agent or the sync, or by the owner before the latest T3 activity of its threads. It never moves an item out of `done` or `not_relevant`, and never sets `done` on an item in `future` or `todo`. Each change is a compare-and-set on `version`; a conflict skips the item for this run.
- **Every run reads full state, not a delta, and keeps no boundary.** Each run reads every top-level thread of every T3 project and applies the status rules to every item that has a linked thread, settled or not, whatever its age. Applying is idempotent (unique thread id, compare-and-set), so an item skipped on a `version` conflict or a failed record is decided again on every later run until it agrees; per-record errors are recorded in `sync_runs` and never stop the run.
- **Snapshots out of order never roll back.** A thread record whose `updatedAt` is not newer than the stored last activity of its link is ignored (equal is nothing new). A security family, or the open Issues count, whose as-of time is older than the stored one keeps the stored values.
- **Missing items:** every unsettled top-level thread with no item and no suppression gets one, whatever its age, titled from the thread, in the project mapped from its T3 project. A settled thread with no item gets one (as `done`) only when it settled in the last 7 days; older finished work is not imported. Both rules depend only on the thread, so a failed creation is retried on every run while the rule still holds. Items created by the first run are flagged as imported and are not "new since your last visit".
- **Top-level threads only.** A thread with a `parentThreadId` (subagent, delegated task, partner review) never gets its own item. The agent instruction tells such agents not to call Mikud; `mikud_start_thread` takes the caller's `parentThreadId` from T3 and refuses with `not_top_level` when it is set; and the sync moves any link it finds on a child thread to the parent's item.
- **Order before the morning message:** the morning message is fixed at 08:00 Asia/Jerusalem, Sunday to Friday (requirements section 5), and the reconciler runs at 07:30 on the same days: the `overview` collector, then the T3 read, then the push. When it fails or the PC is off, the morning message and the board show the time of the last successful sync and the as-of time of the security data.
- **Untrusted text:** thread titles and repository data are data. The sync tool passes them only as JSON to the API, never into a shell command or a prompt.

### Security design

Status: Better Auth used only as it documents itself (owner's decision, 2026-11-02; the design and its gaps are in the owner's notes). Agent keys, owner and agent rights, the CSRF check and the secret check are implemented. The Telegram and morning-message rules are implemented (row 8). The deployment notes, including "after a restore", exist in [deployment.md](deployment.md) (row 13).

- **Network:** production is reachable only over NetBird; the owner configures it. The development stack binds to `127.0.0.1` only.
- **The rule:** authentication goes through Better Auth's built-in features, configuration, official plugins (`username`, `twoFactor`, `@better-auth/api-key`, the core `deviceAuthorization` and `bearer`) and documented hooks only. Mikud does not wrap its handler, lock around it, keep its own session clocks or proofs, or post-process its answers. What those features do not guarantee is an owner gap (below), not Mikud code.
- **Keys:** `MIKUD_AUTH_SECRETS` (Better Auth's versioned `secrets`, `2:new,1:old`; the first signs and encrypts, the others decrypt) and the optional `MIKUD_AUTH_SECRET` (its legacy `secret`, for data from before `secrets`). `MIKUD_SETTINGS_KEYS` encrypts the secrets stored in Settings (AES-256-GCM, HKDF per key, the column as additional data), never shared with auth. The server refuses to start while a `BETTER_AUTH_*` or `AUTH_SECRET` variable is set, because Better Auth would read it on its own.
- **Owner rights:** everything, including delete, stage change, settings and the account. **Agent rights:** everything else in requirements section 3: no delete, no stage change (proposals only), no settings.
- **Agent keys:** Better Auth's api-key plugin: `mkd_` and 64 letters, each with a name and an end (1 to 365 days, `keyExpiration`), stored hashed, listed and disconnected (deleted) in Settings (the plugin's list answers at most 100 keys, the database adapter's default; Settings shows what it answers, and Disconnect all lists again until the list is empty); its per-key rate limit (10 a day by default) is off, `enableSessionForAPIKeys` is off, so a key never becomes a session. The API and MCP verify a bearer key with `verifyApiKey`. A documented `hooks.before` refuses `/api-key/*` from a browser while the account has no two-factor, and any key prefix but `mkd_`. The secret check refuses `mkd_` keys in agent text. There is no owner key.
- **Agent approval (owner's decision, 2026-11-02, design B of the lab):** `mikud connect` (the sync bundle) runs Better Auth's core `deviceAuthorization` for the one client id `mikud-connect` (`validateClient`; the code lives 10 minutes, polls every 5 seconds). The owner opens `/connect/device`, signed in with two-factor (a `hooks.before` refuses `GET /device`, approve and deny while the account has none), compares the code and allows or denies. The CLI then receives a session token, sends it as `Authorization: Bearer` (Better Auth's `bearer()`, as the device page documents) to `/api-key/create` with its `--name` and `--days`, and ends that session with `/revoke-session` in a `finally`. The UI has no button that creates a key; the CLI creates one key in the normal flow. A signed-in owner session can still call `/api-key/create` (that follows from G-B).
- **Header contract:** agents send `Authorization: Bearer <key>` to `verifyApiKey`; there is no session fallback, `/mcp` takes keys only, `enableSessionForAPIKeys` stays off. Browser paths (`/api/v1`, `/api/setup/status`) give `getSession` the `Cookie` header alone. On Better Auth's routes a `hooks.before` refuses an `Authorization` header everywhere except `/api-key/create` and `/revoke-session`, where a bearer may end only its own session; with a cookie or without.
- **Browser sign-in:** one account; a username and a password (12 to 128 characters), then a TOTP code or a backup code. The username is 3 to 30 letters, digits, underscores and dots, with no dot first, last or next to another dot (the username plugin's documented `usernameValidator`), so the synthetic e-mail Better Auth requires is the lowercased username at `mikud.local`. Better Auth's two-factor plugin names the authenticator account after the e-mail and has no option for it, so the setup page drops `@mikud.local` from the label of the QR code and the app shows the username (`authenticatorUri`, owner's decision, 2026-11-03); the query with the secret stays as Better Auth wrote it. The first owner comes from Better Auth's sign-up, refused once an owner exists (a `hooks.before` before hashing, `databaseHooks.user.create.before`, and the single-owner index). Better Auth cannot require two-factor, so Mikud's API accepts a session only while the account has it on (`user.twoFactorEnabled`); right after enrolment the setup page calls Better Auth's `revokeOtherSessions`. A challenge lives 180 seconds (`twoFactorCookieMaxAge`); `trustDevice` is refused on every route that accepts it; the account locks for 15 minutes after 10 wrong codes. Cookies are `HttpOnly`, `SameSite=Lax` (Telegram deep links open with them), `Secure` with an https public URL.
- **Routes:** a documented `hooks.before` admits a fixed list of Better Auth's route patterns over HTTP (among them `/revoke-session` and the plugin's five device routes) and answers 404 to every other one, including routes a later version adds. Server calls are not HTTP requests and pass.
- **Rate limits and the client address:** Better Auth's limiter, stored in the database, 5 per 5 minutes on every credential route. The address comes from `X-Forwarded-For` behind the proxies in `MIKUD_TRUSTED_PROXIES`; this holds only while Mikud is reachable through Traefik alone and Traefik replaces client forwarding headers (deployment.md). Mikud's own limit on failed agent keys counts by socket address.
- **Signing out after days without Mikud open:** Better Auth's sliding `expiresIn` (Settings, 1 to 90 days, default 30) with `updateAge` 1 hour and `deferSessionRefresh`: a read never extends a session; the Better Auth client's own refresh does (opening the page, refocusing it, coming back online, another tab's change), through the transport fix below. `freshAge` is 0. A change rebuilds the Better Auth instance in place; requests in flight finish on the old one.
- **The Account page** (`/account`, from the account menu; `/settings/account` leads there): the signed-in browsers (a session of `mikud connect` is named so) and signing out one of them (Better Auth's `revokeSession`), change password in a dialog (Better Auth's `changePassword` with `revokeOtherSessions`), sign out the others, sign out everywhere, new backup codes, a new authenticator, and the recovery command. Signing out this browser (Better Auth's `signOut`) is in the shell's account menu; it asks about unsaved changes first and drops them only once the sign-out worked. All on Better Auth's routes.
- **Recovery:** `node dist/server/cli.js reset-password` in the container runs Better Auth's documented reset (`requestPasswordReset` with a local sender, then `resetPassword`, as server calls, with `revokeSessionsOnPasswordReset`): a new random password printed once, every session ended, two-factor kept. Without the authenticator, the backup codes saved at enrolment are the way in.
- **Audit:** documented hooks write the rows on Mikud's own connection: `databaseHooks` for setup, sign-in, two-factor changes, password changes and ended sessions; `hooks.before` for agent keys, agent approvals (`device.approve`, `device.deny`) and new backup codes; `databaseHooks.session.create.before` for the session `/device/token` gives (`session.connect`); `hooks.after` for sign-out and `/revoke-session`. A failing audit write refuses the change, except sign-out and `/revoke-session`, which are recorded after the fact and never throw (a throwing sign-out hook is swallowed by Better Auth and would leave the session valid; a refused `/revoke-session` would leave the device session alive).
- **Logs:** Better Auth's logger and `onAPIError.throw` route every error through Mikud's log, which records the class, SQLSTATE and code only.
- **Gaps the owner accepted (2026-11-02):**
  - G1: only the Better Auth client's refresh counts as activity, not keyboard or mouse input.
  - G2: a shorter idle length does not shorten browsers already signed in; sign out everywhere does.
  - G3: a two-factor challenge opened before the recovery reset can still be finished within its 180 seconds.
  - G4: with the authenticator and every backup code lost, no browser signed in and OTP off, only editing the database brings the owner back.
  - G5: an audit row is not in the change's transaction; a row can remain for a change that then failed, and a sign-out is recorded after the fact.
  - G6: a password sign-in that runs exactly while two-factor is enrolled can keep a session that never passed the second factor.
  - G7: enrolment is not atomic: (a) a crash between its steps falls under G4; (b) when the setup page closes before it signs out the other browsers, a password-only session stays.
  - G10 (changed with `bearer()`, accepted by the owner (2026-11-02)): a script running in the Mikud page can impersonate the owner fully.
    - `bearer()` answers every response that sets the session cookie (sign-in, the second factor, a password change) with a `set-auth-token` header holding the value of that cookie, signed, and exposes it to page script (`Access-Control-Expose-Headers`). The cookie is `HttpOnly`; the header is not. Sent back as the session cookie from anywhere, without `Authorization`, that value is the owner's session: every owner route, Settings, the account, deleting, agent keys (pinned as a regression test, "G10, accepted by the owner (2026-11-02)", in `src/server/http/agent-approval.integration.test.ts`). The `Authorization` allow-list does not limit it, because it is a cookie.
    - The browsers list also hands the page the other sessions' raw tokens, and `bearer()` accepts an unsigned token, so the signature no longer protects them; as `Authorization: Bearer` they reach only `/api-key/create` and `/revoke-session` of their own session (the `hooks.before` allow-list), which still lets them create an agent key.
    - What stands against it: the Content-Security-Policy (`script-src 'self'`, `connect-src 'self'`: scripts only from Mikud itself, no requests to other origins), escaping every value the page shows, the private network (NetBird only) and the single user. Mikud does not strip the header or rewrite Better Auth's answers (the rule above); removing `bearer()` would remove the device flow's documented way to use its token.
  - G14: every browser signs in once more after the upgrade.
  - G15: there is no owner token; owner actions need the signed-in browser.
  - G18: agent keys outlive sign-outs, and a session left from G6 or G7 can create one.
  - G-A: an agent's name and days are chosen in its `mikud connect` command, not on the approval page (Better Auth's device flow carries neither).
  - G-B: between `/device/token` and `/revoke-session` the CLI holds a full owner session, reduced by the `Authorization` allow-list above. Its lifetime is no separate option: it is the session's `expiresIn`, the idle days of Settings (1 to 90, default 30). If the CLI dies before it ends the session, the session stays until then; the Account page lists it as "mikud connect (agent approval)" and signs it out.
  - OTP through Telegram is the owner's choice, off by default: when on, the Telegram chat becomes a way in.
- **Transport fix at the `/api/auth` mount (owner's decision, 2026-11-02):** The Better Auth client sends its session refresh (`POST /get-session`) without a body, `@hono/node-server` gives every POST a body stream, and better-call then requires a `Content-Type` (415). The `/api/auth` mount therefore passes a request without content (not GET or HEAD, `Content-Length: 0`, no `Transfer-Encoding`) with a null body (`withoutEmptyBody` in `src/server/app.ts`); everything else passes through unchanged. A transport fix, not a Better Auth change: remove it when upstream sends no body for empty requests.
- **Owner settings and the environment:** every setting the owner manages lives in Settings with a default. An environment variable may set the Telegram bot token, the chat id or the private domains; it overrides the stored value for that field only, and the UI shows the field locked with the variable's name. Only the database connection, file paths, deployment wiring (`MIKUD_PUBLIC_URL`, `MIKUD_TRUSTED_PROXIES`, `TELEGRAM_API_URL`) and the keys stay in the environment alone.
- **After a restore:** a restored database may hold sessions ended after the backup was taken, and agent keys disconnected since. The deployment notes tell the owner to sign out everywhere and check Agent access after any restore (or run the recovery command), and to replace `MIKUD_AUTH_SECRETS` if it may have leaked.
- **CSRF:** Better Auth's origin check, JSON-only bodies and Fetch Metadata on sign-up guard `/api/auth` (on in every environment, also under `NODE_ENV=test`); every state-changing request to `/api/v1` from a browser must carry a custom header and an `Origin` equal to the configured public URL.
- **Telegram:** only the configured owner chat id is served. Every update is recorded by `update_id` in the same transaction as the item and its audit row; the next poll's `offset` acknowledges only updates whose transaction committed, and a repeated `update_id` does nothing.
- **Morning message once a day:** a `job_runs` row for the local date is written as `sending` before the send and `sent` after. On start, a run left in `sending` becomes `unknown` and is not sent again (at most once, never twice). A send that may have reached Telegram (timeout, dropped connection, a 5xx or an answer that is not Telegram's JSON, such as a gateway's error page) also becomes `unknown`; only a definite failure (Telegram's own JSON answer with `ok: false` and a 4xx code, or no connection at all) becomes `failed` with its code and is retried on the next 30-second tick. A missed time is sent late only until 3 hours after the configured time (11:00), with no note; after that the day is `skipped` and the status route shows it.
- **Bot text:** the bot's captures pass the same secret check as agent text; a refusal is answered without repeating the text.
- **Secrets in agent text:** text written with the agent token is checked against high-confidence patterns only: known token formats (GitHub, OpenAI and Anthropic keys, Slack, AWS access keys, Google API keys, Telegram bot tokens, JWTs), private key blocks (redacted whole, BEGIN through END or to the end of the text when END is missing), credentials in URLs (`user:password@`), Mikud's own agent keys (`mkd_` and 64 letters), assignments such as `password=`, `token:` or `secret=` followed by a value that is not a placeholder (`***`, `<...>`, `[redacted]`), environment-style assignments whose name ends in TOKEN, SECRET, PASSWORD, PASSWD, KEY or APIKEY (`MIKUD_OWNER_TOKEN=...`, `DB_PASSWORD: ...`) with any value of 8 or more characters that is not a placeholder (lower-case words and hex included), IPv4 addresses outside documentation ranges and loopback, and host names under the private domains set in Settings (or by `MIKUD_PRIVATE_DOMAINS`); a save applies them without a restart. Commit SHAs and checksums pass. A refusal returns `secret_suspected` with the rule name, never the matched text. Text from the sync tool (thread titles) is not refused: matches are replaced with `[redacted]`, so one record cannot stop a run. This is a safety net, not a promise that every secret is caught.
- **Untrusted text:** thread titles, comments and item text are data. The UI escapes everything; the morning message escapes Telegram HTML.
- **Logs:** no tokens, cookies or message text in logs.

## Required workflow contracts

The four workflow scripts are Bash with `#!/usr/bin/env bash`, LF line endings and the executable bit, run inside WSL, resolve the repository root from their own location, and run Node, pnpm, shellcheck and shfmt inside the toolchain container. Development and test data live on the Linux file system, not under `/mnt/c`. `scripts/ci-result.sh` is Bash too but runs only on the GitHub runner, inside the Release workflow.

- `scripts/local.sh build|up|start|down|status|logs|nuke`: builds `mikud:dev` explicitly, runs `docker-compose-dev.yml` (fails with a clear message when it is missing), checks health and that the application process is not UID 0. `down` keeps the database directory; `nuke` asks for confirmation and deletes only the validated development database directory.
- `scripts/verify.sh [--changed [BASE]] [--guards-only] [--skip-e2e]`: the one verification entry point used locally and in CI: guards, Biome, types, unit tests, HTTP and MCP tests against a disposable PostgreSQL, builds, the container with health and UID checks, then Playwright. Cleans up its stack.
- `scripts/try-pr.sh <number>|status|restore`: builds the pull request in a disposable worktree and runs it as a separate Compose project with its own disposable PostgreSQL seeded with invented fixtures, its own generated tokens and Telegram off (no bot settings; a stand-in Telegram API comes with row 8 if the bot needs one to start). It never touches the development stack, its database or its `.env`, which hold real data and the real bot token after the dry run. `restore` removes the PR stack. Never pushes, merges or touches the user's checkout.
- `scripts/release.sh`: run by the Release workflow on `main`: preflight (clean, synchronized, full verify), version bump chosen by the operator, changelog section closed, release commit and immutable tag, image pushed to GHCR, GitHub Release. Has a dry run. Never deploys.
- `scripts/ci-result.sh --sha SHA (--wait | --expect-run ID)`: run by the Release workflow. Finds the newest CI run of the commit: runs of the workflow file `ci.yml` (by its workflow id) with that head commit on `main`, started by `push` or `workflow_dispatch` (never pull request or scheduled runs; the CI a release runs through `workflow_call` belongs to the Release run and is not listed under `ci.yml`), newest by creation time, judged by the run's current record (its latest attempt), with exact values compared inside `jq`. Only that run counts: an older green run of the same commit is never used instead. `--wait` waits for a queued or running one (30 minutes of elapsed time, looking again every 30 seconds and selecting again each time; each API call is limited to 30 seconds) and prints `reuse=true` only when it ended in success; anything else, including an API answer that fails or is unexpected or more runs than one page, gives `reuse=false`. `--expect-run` repeats the selection without waiting and fails unless the newest run is still that run and its latest attempt succeeded. Prints `reuse=`, `run_id=` and `reason=` for `GITHUB_OUTPUT`; needs `gh`, `jq` and `timeout`. `scripts/test-ci-result.sh` runs it against a stand-in `gh` with the guards, in the toolchain container (which has `jq` for it).
- `scripts/test-release-workflow.sh`, run with the guards: reads the job and step conditions and the Release step's script from `release.yml`, evaluates the conditions with Node for the reused-CI and fresh-CI paths with and without `dry_run` (and for a failed, cancelled or skipped find or CI, a cancelled run and a branch other than `main`), and runs the step's script with stand-ins to check that `dry_run` passes `--dry-run` to `release.sh`.

## CI and GitHub

- One CI workflow: a change-detection job, area jobs gated by it, and a final `summary` job that passes when skipped areas were not affected. Pull request runs cancel superseded runs; `main` runs are not cancelled. Manual full run and a weekly scheduled full run. Least-privilege permissions; actions pinned to commit SHAs.
- Release workflow (`.github/workflows/release.yml`, **Release**, run by hand on `main` with patch, minor or major, and an optional `dry_run`): `Find a green CI run` (`scripts/ci-result.sh --wait`, with `actions: read`) reuses the newest CI run of the commit on `main` when its latest attempt succeeded; otherwise, or when its result cannot be read, `Verify` calls `ci.yml` (`workflow_call`) on the commit. `Release` runs only on `main`, after the find succeeded and either a reused run (with `Verify` skipped) or a green `Verify`; a failed or cancelled find or `Verify` releases nothing. When it reuses a run, the workflow repeats the selection right before `release.sh` (`--expect-run`, stopping if a newer run appeared or the run started again); `release.sh` itself does not look at CI runs. Then it runs `scripts/release.sh --skip-verify --expect-sha <that commit>`, with `--dry-run` when `dry_run` is set, with `contents: write`, `packages: write` and `actions: read` for that job only. A dry run takes the same path as a release, the re-check of a reused run included, and publishes nothing. Runs never overlap and a running release is never cancelled; a press while one runs waits, and a later press replaces one that is still waiting. To continue a release that stopped, start a new run (Run workflow): after the release commit is on `main`, "Re-run failed jobs" keeps the old commit and stops at `--expect-sha`. CI's concurrency group carries the workflow name, so a release's CI is never held behind or replaced by the CI of `main`. The release commit is pushed with the workflow token, which does not start the CI of `main` again; it changes only `package.json` and `CHANGELOG.md`. So a run that finishes a stopped release, whose commit is then the release commit, finds no CI run to reuse and runs the CI itself.
- Manual check after the merge (agents may do it, `dry_run` only): run Release with `dry_run` once after the CI of `main` is green, and confirm in the run that `Verify` was skipped, `Check the reused CI run again` passed and `release.sh` printed its dry-run plan. The fresh-CI path is covered by `scripts/test-release-workflow.sh`, and on GitHub by the first dry run whose commit has no green CI run on `main`.
- Dependabot weekly for npm, GitHub Actions and Docker; minor and patch grouped; majors separate; no auto-merge.
- Repository settings like the owner's other public repositories: default branch `main`, secret scanning with push protection, Dependabot alerts and security updates, Actions default token read-only, no rulesets. Pull requests are squash-merged only when every check is green, and the merged branch is then deleted locally and on GitHub.
