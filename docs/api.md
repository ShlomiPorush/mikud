# Mikud HTTP API and MCP tools

Status: implemented in `src/server/http/`, `src/server/auth/`, `src/server/settings/` and `src/server/mcp/`; request bodies are the zod schemas in `src/shared/api.ts`. The UI, the Telegram bot and the sync tool build on this contract. Product rules are in [requirements.md](requirements.md); the sync rules in "Agent and sync rules" of [project-foundation.md](project-foundation.md).

## Conventions

- Base path `/api/v1`. JSON in and out (`Content-Type: application/json`). Bodies are limited to 512 KiB, sync snapshots to 16 MiB.
- Success: `{"data": ...}`. Paged lists: `{"data": [...], "nextCursor": "..." | null}`; pass `cursor=<nextCursor>` for the next page. `201` for a created resource, `204` (no body) for a delete.
- Error: `{"error": {"code": "<code>", "message": "<for people>", ...details}}`. Branch on `code`, never on `message`.
- Times are ISO 8601 strings in UTC. Ids are UUIDs, except T3 thread and project ids (opaque strings, up to 200 characters).
- Codes (stage, status, type, severity, actor kind) are the English codes of `src/shared/enums.ts`. Labels come from the locale files.
- Unknown body fields are ignored. A path id that is not a UUID answers `not_found`.

## Authentication

Every route under `/api/v1` needs one of:

- **An agent key**: `Authorization: Bearer <key>`. An agent or the sync gets one through `mikud connect` (below), after the owner approves it in the browser (Better Auth's `@better-auth/api-key` plugin): `mkd_` and 64 letters, a name and an end date, stored as a SHA-256 hash. The server checks a key with the plugin's server-only `verifyApiKey`; a valid key acts as an agent. An agent may add `X-Mikud-Agent: <name>` (letters, digits, space, `._:-`, up to 60 characters); the audit log then shows `agent:<name>`. A key never becomes a session.
- **The owner's browser session** (Better Auth, below), which acts as the owner. Better Auth has no option that requires two-factor, so Mikud accepts a session only while the account has two-factor on (`user.twoFactorEnabled`); otherwise `403 totp_required`. Every request that is not `GET`, `HEAD` or `OPTIONS` must also send `X-Mikud-Request: 1` and an `Origin` equal to the origin of `MIKUD_PUBLIC_URL`, or it is refused with `forbidden`. A session never stands in for a key where a key is required: the sync routes answer it `forbidden`, and `/mcp` accepts keys only.

A request with an `Authorization` header is an agent request: when both are present the key is used, and a wrong key is refused (`401`), never read as the cookie's session. The browser paths (`/api/v1`, `/api/setup/status`) give Better Auth's `getSession` the `Cookie` header alone, so a session token sent as `Authorization: Bearer` (which Better Auth's `bearer()` plugin accepts on its own routes) is never a session there. Failed keys count per client address (the socket's): after 10 within a minute, every bearer request from that address answers `rate_limited` until the minute is over. Reading a session never extends it (`deferSessionRefresh`).

Rights: the owner may do everything. An agent may do everything else except delete, change a stage, decide proposals, create projects, rename or re-link a project, and read or change settings and suppressions (`forbidden`). Text written by an agent is checked for secrets (`secret_suspected`). There is no owner key: owner actions need the signed-in browser.

Writes record an audit row with the actor and a source: `ui` (browser session), `api` (agent key), `mcp`, `sync` (the sync routes), `telegram` (the bot, in process), `cli` (the recovery command on the server).

### Browser sign-in

One account, the owner's: a username, a password and a second factor, through Better Auth (`better-auth` 1.7.15) under `/api/auth`, used as it documents itself. The UI calls Better Auth's client; there is no Mikud route in between. Sessions are cookies (`better-auth.session_token`, with the `__Secure-` prefix when `MIKUD_PUBLIC_URL` is `https`), `HttpOnly`, `SameSite=Lax`.

**Open routes.** A documented `hooks.before` admits only these route patterns over HTTP; every other path answers `404` (`/sign-in/email`, `/update-user`, `/request-password-reset`, `/reset-password/:token`, `/callback/:id`, `/api-key/update` and every route a later version adds). Server calls (`auth.api.*`) are not HTTP requests and are not limited by it.

| Method and path                                                              | Use                                                                                                                                                                                                  |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`, `POST /get-session`                                                   | The session. `GET` never extends it and says `needsRefresh`; the client's own `POST` extends it                                                                                                      |
| `POST /sign-up/email`                                                        | First run (below)                                                                                                                                                                                    |
| `POST /sign-in/username`                                                     | `{username, password}`. An owner with two-factor gets `{twoFactorRedirect: true, twoFactorMethods}` and a challenge cookie that lives 180 seconds; without two-factor, a session that may only enrol |
| `POST /sign-out`                                                             | Ends this session                                                                                                                                                                                    |
| `POST /change-password`                                                      | `{currentPassword, newPassword, revokeOtherSessions: true}`: the other browsers are signed out; this one gets a new session                                                                          |
| `GET /list-sessions`, `POST /revoke-other-sessions`, `POST /revoke-sessions` | The browsers list, sign out the others, sign out everywhere                                                                                                                                          |
| `POST /two-factor/enable`                                                    | `{password}`: `{totpURI, backupCodes}` (10 codes, shown once)                                                                                                                                        |
| `POST /two-factor/verify-totp`                                               | `{code}`: finishes enrolment (session) or sign-in (challenge cookie)                                                                                                                                 |
| `POST /two-factor/verify-backup-code`                                        | `{code}`: sign-in with a saved backup code; each works once                                                                                                                                          |
| `POST /two-factor/generate-backup-codes`                                     | `{password}`: 10 new codes; the old ones stop working                                                                                                                                                |
| `POST /two-factor/disable`                                                   | `{password}`: before setting up a new authenticator                                                                                                                                                  |
| `POST /two-factor/send-otp`, `POST /two-factor/verify-otp`                   | Only while Settings sends sign-in codes to Telegram (off by default): the code goes to the owner's chat                                                                                              |
| `POST /revoke-session`                                                       | `{token}`: ends one session (the Account page; and `mikud connect` ending its own)                                                                                                                   |
| `POST /api-key/create`, `GET /api-key/list`, `POST /api-key/delete`          | Agent keys: `{name, expiresIn}` (1 to 32 characters; 1 to 365 days in seconds) answers the key once; `list` shows name, start, created, ends, last request; `delete {keyId}` disconnects it at once  |
| `POST /device/code`, `POST /device/token`                                    | Agent approval, for `mikud connect` (no session): a code for client id `mikud-connect`, then its answer (below)                                                                                      |
| `GET /device`, `POST /device/approve`, `POST /device/deny`                   | Agent approval, for the owner's browser on `/connect/device`: claim the code, then answer it once                                                                                                    |
| `GET /ok`                                                                    | Better Auth's health answer                                                                                                                                                                          |

- **Refused by Mikud's hooks:** `trustDevice: true` on every route whose body accepts it (`400 TRUST_DEVICE_UNSUPPORTED`: there are no trusted devices); `/api-key/*`, `GET /device`, `/device/approve` and `/device/deny` while the account has no two-factor (`403 TOTP_REQUIRED`); an `Authorization` header on any route but `/api-key/create` and `/revoke-session`, with or without a cookie (`403 AUTHORIZATION_NOT_ALLOWED`); `/revoke-session` with a bearer for another session than the bearer's own (`403 OWN_SESSION_ONLY`); a key `prefix` other than `mkd_` (`400 INVALID_KEY_PREFIX`); a sign-up once the owner exists (`403 ALREADY_SET_UP`).
- **CSRF:** Better Auth's own: a `POST` that carries cookies must come from `MIKUD_PUBLIC_URL`'s origin (`403`), bodies must be JSON (`415` otherwise), and sign-up checks Fetch Metadata.
- **Rate limits:** Better Auth's limiter, stored in the database: every credential route (sign-up, sign-in, the two-factor routes, the password) allows 5 requests per 5 minutes per address and route, `/device/code` 10 per 10 minutes, `/device/token` 300 per 15 minutes (a code's whole lifetime of polling), `GET /device` 5 per 10 minutes (the plugin's own), everything else 100 a minute. A route's count restarts only after it has been quiet for a whole window. `mikud connect` treats a 429 while polling as `slow_down`. The address is read from `X-Forwarded-For` behind the proxies in `MIKUD_TRUSTED_PROXIES` (see the condition in [deployment.md](deployment.md)). Two-factor also locks the account for 15 minutes after 10 wrong codes.
- **Server errors:** an unexpected failure inside Better Auth answers `500 internal_error`; the log holds only its class, SQLSTATE and code, never its message, query or values.
- **Audit**, from Better Auth's documented hooks, on Mikud's own connection: `account.setup`, `session.sign_in` (`{stage: "password"}` for every session created after a password, also one the plugin turns into a challenge; `{stage: "second_factor", method}` after a code), `account.totp_enable`, `account.totp_disable`, `account.password_change`, `account.password_reset`, `account.backup_codes_new`, `session.end` (one per session ended by sign out others, everywhere or the reset), `api_key.create` (source `api` when `mikud connect` creates it), `api_key.delete`, `device.approve`, `device.deny`, `session.connect` (the session `/device/token` gives), and `session.sign_out` and `session.revoke` after the fact. A failing audit write refuses the change, except sign-out and `/revoke-session`, which are recorded after the fact and never refused. The row is not in the change's transaction (gap G5 in the foundation plan).

**Sign out after days without Mikud open** (Settings, `sessionIdleDays`, 1 to 90, default 30): Better Auth's sliding `session.expiresIn` with `updateAge` 1 hour. Only the Better Auth client's own refresh extends a session: opening Mikud, bringing its tab back to the front, coming back online, or a session change in another tab. Mikud's polling never does. **Transport note:** The Better Auth client sends its session refresh (`POST /get-session`) without a body, `@hono/node-server` gives every POST a body stream, and better-call then requires a `Content-Type` (415). The `/api/auth` mount therefore passes a request without content (not GET or HEAD, `Content-Length: 0`, no `Transfer-Encoding`) with a null body (`withoutEmptyBody` in `src/server/app.ts`); everything else passes through unchanged. A transport fix, not a Better Auth change: remove it when upstream sends no body for empty requests. A change rebuilds the Better Auth instance at once; a shorter value does not shorten browsers already signed in until their time left falls under it (use sign out everywhere).

### Agent approval (`mikud connect`)

An agent or the sync gets its key in the browser: Better Auth's core `deviceAuthorization` plugin, its `bearer()` plugin and the api-key plugin, used as documented. `mikud connect` is a subcommand of the sync bundle (see [sync.md](sync.md)).

1. The CLI sends `POST /api/auth/device/code {client_id: "mikud-connect"}` (the only client id `validateClient` accepts) and gets `device_code`, `user_code` (8 letters and digits), `verification_uri` (`<public URL>/connect/device`), `verification_uri_complete`, `expires_in` 600 and `interval` 5. It prints the link and the code and opens the browser.
2. The owner opens `/connect/device?user_code=…`, signs in when needed, and the page calls `GET /device?user_code=…`, which claims the code for this session. It shows the code to compare, then Allow (`POST /device/approve {userCode}`) or Deny (`POST /device/deny`). A code is answered once; an expired one answers `400 expired_token`.
3. The CLI polls `POST /device/token {grant_type: "urn:ietf:params:oauth:grant-type:device_code", device_code, client_id}` every `interval` seconds: `authorization_pending`, `slow_down` (it then waits 5 seconds longer), `access_denied`, `expired_token`, or `{access_token, token_type: "Bearer", expires_in}`. An approved code is redeemed once, also when polls race.
4. The access token is a full owner session (gap G-B in the foundation plan), with `User-Agent: mikud-connect`, lasting what every session lasts (the idle days). The CLI sends it as `Authorization: Bearer` to `POST /api-key/create {name, expiresIn}`, then, whatever happened, to `POST /revoke-session {token}` with its own token. Mikud's hook lets the header reach those two routes only.
5. The key goes to the sync's env file, or into Claude Code or Codex through their own `mcp add` commands; it is printed once only when a client's command is missing or fails. Settings, Agent access lists it; Disconnect deletes it and its next request is refused. `GET /api-key/list` answers at most 100 keys (the database adapter's default; `total` counts those), so Disconnect all lists and deletes again until a list comes back empty, and says how many are left when it stops early.

**Gap G10, accepted by the owner (2026-11-02)** (foundation plan): `bearer()` adds a `set-auth-token` header to every answer that sets the session cookie (sign-in), holding the signed cookie value and readable by page script; sent back as the cookie, it is the owner's session on every route. The Content-Security-Policy (`script-src 'self'`) is what keeps other scripts out of the page.

Name and days come from the command, not from the approval page (gap G-A). A signed-in owner session can still call `/api-key/create` itself: the UI has no button for it.

| ------------------------------ | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/setup/status`        |                                                      | `{hasUser, session: "none" \| "enrol" \| "active"}`: whether the owner exists, and whether this browser's session may only enrol or the account has two-factor                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `POST /api/auth/sign-up/email` | `{name, email, username, displayUsername, password}` | Better Auth's sign-up, signed in after it. ### Recovery

`node dist/server/cli.js reset-password`, run in the container on the server, resets the password through Better Auth's documented flow (`requestPasswordReset` with a local sender, then `resetPassword`, as server calls): a new random password printed once, every session ended, two-factor unchanged. Audit rows `session.end` and `account.password_reset` (actor `system`, label `cli`, source `cli`). The reset routes are closed over HTTP. Without the authenticator, the backup codes saved at enrolment are the way in.

## Shapes

Fields are always present; `null` when unset.

- **Item**: `id, projectId (null: inbox), type, status, title, body, severity (security only), goalId, version, statusSetBy, statusSetAt, createdBy, imported, createdAt, updatedAt, closedAt (set exactly when status is done or not_relevant)`.
- **ItemSummary**: `id, projectId, projectName, type, status, title, severity, goalId, version, statusSetBy, createdAt, updatedAt, closedAt`.
- **Project**: `id, name, slug, t3ProjectId, githubRepo ("owner/name"), stage (null until the owner sets one), whereWeAre, openIssuesCount, openIssuesAsOf, createdAt, updatedAt`.
- **GoalProgress**: `id, text, createdAt, done, total`: `done` items linked to the current goal out of `total` items linked to it.
- **Goal**: `id, projectId, text, createdAt, closedAt`.
- **ThreadLink**: `id, itemId, threadId, t3ProjectId, title, lastStatus (T3's status), settled, lastActivityAt, linkedAt`.
- **Comment**: `id, itemId, authorKind, authorLabel, text, threadId, noteId, createdAt`. `noteId`: the note this comment points to (set when the Telegram bot moved the item's text into a note; null when that note was deleted).
- **Note**: `id, projectId (null: a general note), title, body (Markdown, up to 100,000 characters), version, createdBy, createdByLabel, updatedBy, updatedByLabel, createdAt, updatedAt`.
- **NoteSummary**: a Note without `body`, with `excerpt`: the start of the body as plain text on one line (Markdown marks dropped, link text kept), up to 240 characters.
- **NoteVersion**: `id, noteId, version, title, body, projectId, authorKind, authorLabel, restoredFrom (the version it restored, or null), createdAt`. `projectId` is the project the note was in; that project may have been deleted since.
- **NoteVersionSummary**: `version, title, projectId, authorKind, authorLabel, restoredFrom, createdAt, bodyLength`.
- **StageProposal**: `id, projectId, proposedStage, reason, authorKind, authorLabel, state (open, accepted, rejected), createdAt, decidedAt`.
- **SecuritySource**: `id, projectId, family (dependabot, code_scanning, secret_scanning, overview), coverage (enabled, not_enabled, no_access, error, unknown), critical, high, medium, low, asOf, updatedAt`.
- **SyncRun**: `id, kind (t3, security), startedAt, finishedAt, outcome (succeeded, partial, failed; null while running), counts {name: number}, errors [{record, code}]`.
- **SyncResult**: `runId, outcome, counts, errors`.
- **Suppression**: `id, kind (thread, project), externalId, label (what was deleted), createdAt`.
- **Settings**: `id, closedItemDays (1 to 365, default 7), dateFormat, timeFormat, language (he, en), sessionIdleDays (1 to 90, default 30), otpViaTelegram (default false), updatedAt, telegram, privateDomains`. `telegram`: `{botToken: {set, readable, locked, variable}, chatId: {value, locked, variable}, state: "off" | "incomplete" | "on", missing: ("botToken" | "chatId")[]}`: the bot token is never returned; `readable: false` means it was stored with a settings key that is no longer listed. `privateDomains`: `{value: string[], locked, variable}`. A field an environment variable sets is `locked` and names it in `variable`. The formats the UI offers are in `src/shared/datetime-formats.ts`: `dateFormat` is `dd/MM/yyyy` (default), `MM/dd/yyyy`, `dd.MM.yyyy`, `yyyy-MM-dd` or `browser`; `timeFormat` is `HH:mm` (default), `h:mm a` or `browser`. The morning message writes `browser`, and any value not offered, as the default numeric date and the 24-hour clock.
- **AuditEntry**: `id (number), at, actorKind, actorLabel, action, entityType, entityId, before, after, source`. Actions: `item.create|update|delete`, `comment.create`, `note.create|update|restore|delete`, `thread.link|update|move|unlink`, `project.create|update|delete`, `goal.create|close`, `proposal.create|update|accept|reject`, `security.update`, `suppression.create|delete`, `settings.update`, `account.setup|totp_enable|totp_disable|password_change|password_reset|backup_codes_new`, `session.sign_in|sign_out|end|connect|revoke`, `api_key.create|delete`, `device.approve|deny`, `telegram.test_message`. The list is `AUDIT_ACTIONS` in `src/shared/enums.ts`; every action has a label in both locale files. Older rows may also hold `device.pair|revoke|revoke_all`, `session.end_others|end_all|sweep` and `auth.repair`. Comment, thread, goal and proposal entries carry the entity of their item (`item`) or project (`project`), so an item's history includes them.

## Routes

"Owner" routes answer `forbidden` to the agent token.

### Session and the overview

| Method and path | Who     | Body or query   | Answer                                                                                                                                                                                                                      |
| --------------- | ------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /session`  | any     |                 | `{actor: {kind, label}, via: "token"\|"session", browserId, expiresAt}`. `expiresAt` (a session only): when it ends unless the Better Auth client refreshes it first                                                        |
| `GET /morning`  | any     | `since?` (time) | Morning (below). `since` is this browser's previous visit unless the query gives one                                                                                                                                        |
| `POST /visits`  | browser | `{at?}` (time)  | `201 {at, previous}`. Call after the overview was shown, with that read's `now`; recorded one minute before `at`, or before now when `at` is missing or later than the server's clock (see below). `forbidden` with a token |

"browser" routes need the owner's browser session (`forbidden` with a key). The password, the browsers list and signing out are Better Auth's routes (above).

**Browser identity:** the first signed-in request of a browser sets `mikud_browser` (a random id, `HttpOnly`, `SameSite=Lax`, for 400 days). It names the browser for "new since your last visit" only and never authenticates; a request with only this cookie is `unauthorized`.

**Morning**:

```text
{
  now, since,
  waiting: [ {kind: "item", at, item: ItemSummary}            // status waiting_on_you
           | {kind: "stage_proposal", at, proposal: {id, projectId, projectName, currentStage,
                                                      proposedStage, reason, authorKind, authorLabel, createdAt}} ],
  new: [ {change: "created" | "updated", item: ItemSummary} ],
  security: [ {projectId, projectName, stage, critical, high, alerts: {critical, high},
               items: {critical, high}, asOf, stale} ],
  agentUpdates: [ {projectId, projectName, generalNotes, updates: [
      {kind: "comment", at, itemId, itemTitle, actorKind, actorLabel, text}
    | {kind: "status",  at, itemId, itemTitle, actorKind, actorLabel, from, to}
    | {kind: "note",    at, noteId, noteTitle, actorKind, actorLabel, change: "created" | "updated"} ]} ],
  projects: [ {id, name, slug, stage, goal: GoalProgress | null, whereWeAre, openItems,
               openIssues, openIssuesAsOf, repo} ],
  inboxCount,
  sync: {lastSuccessAt, stale, lastPartialAt, securityLastSuccessAt}
}
```

- `now`: the server's time when this read started. A visit recorded with it marks nothing newer than what this read showed as seen. The visit is stored one minute before `now`: a write whose transaction was still open during the read has a time before `now` but at most 30 seconds before it (PostgreSQL ends any transaction of the server after 30 seconds), so it still counts as new on the next visit. Items written in that minute may show as new twice; none is hidden.
- `since`: the `since` query when given; else the browser's latest recorded visit; 24 hours before now on a browser's first visit, and always for token callers. Each browser keeps its own. The UI keeps the `since` of the page's first read and passes it on every refresh, so "new since your last visit" stays stable while the page is open.
- Items shown anywhere in the view: open items, and closed ones closed within `closedItemDays`. Older closed items are only in the archive.
- `new`: created after `since` (`change: "created"`, except items imported by the first sync run) or changed after `since` and after their creation (`"updated"`). Newest first.
- `security`: one line per project with something to say. `critical` counts in every project, `high` only at stage `production` (0 elsewhere). Counts come from enabled `dependabot`, `code_scanning` and `secret_scanning` sources plus open `security` items of the project. `asOf` is the oldest as-of time of the project's enabled sources (null when it has none); `stale` is true when that time is unknown or older than 26 hours.
- `agentUpdates`: comments, status changes and note versions by agents and the sync after `since`, grouped by project, groups and updates newest first, at most 300 of each kind. `projectId: null` is the inbox's items, or the notes without a project when `generalNotes` is true. A note's events come from its versions, so a later edit by the owner does not hide them; `noteTitle` is the note's title now, and a deleted note's events are gone.
- `projects`: projects with at least one open item, by name.
- `sync.lastSuccessAt`: when the last complete T3 run (`succeeded`) finished; a `partial` run may have missed whole projects, so it never counts as fresh. `sync.lastPartialAt`: when the latest `partial` T3 run finished, only when it is later than `lastSuccessAt` (else null). `sync.securityLastSuccessAt`: the latest security run that was `succeeded` or `partial`.
- `sync.stale`: no complete T3 sync, or the last one finished more than 26 hours ago.

### Projects

### Audit filters

`GET /audit` narrows the activity log with query parameters; the Activity page keeps the same names in its address. Every filter is optional, and they combine with AND. A value it cannot read is `validation_failed` (400).

| Parameter                | Value                                                                                                             | Lists                                                                                                                                                                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `actorKind`              | `owner`, `agent`, `bot`, `sync` or `system`                                                                       | Rows by that kind of actor                                                                                                                                                                                                                                                             |
| `agent`                  | An agent label: `agent` or `agent:<name>` (the `X-Mikud-Agent` name, up to 60 letters, digits, spaces and `._:-`) | Rows of kind `agent` with exactly that label                                                                                                                                                                                                                                           |
| `action`                 | An action code (`[a-z_]+\.[a-z_]+`, each part up to 30 characters), also one only older rows hold                 | Rows with that action                                                                                                                                                                                                                                                                  |
| `projectId`              | UUID                                                                                                              | The project's own rows and the rows of the items and notes in that project now (a deleted note's rows show only without this filter; an item's comments and threads are its rows)                                                                                                      |
| `itemId`                 | UUID                                                                                                              | The item's rows, its comments and threads included                                                                                                                                                                                                                                     |
| `q`                      | Text, up to 200 characters, trimmed; empty is no filter                                                           | Rows whose action code, entity type, actor label or name (an item's title, a project's name, a key's label) holds the text, case-insensitive, with `%` and `_` taken literally. With `lang` also the rows whose action or entity type has a label in that language that holds the text |
| `lang`                   | `he` or `en`                                                                                                      | The language whose labels `q` matches (`audit.action` and `audit.entity` in `src/shared/locales`); the UI sends its own                                                                                                                                                                |
| `entityType`, `entityId` | Text                                                                                                              | Rows of that entity (the filters from before these)                                                                                                                                                                                                                                    |

The first page (no `cursor`) also answers `total`, the rows every filter lists, and `counts`, read in one snapshot with the page:

- `actorKind`: `{owner, agent, bot, sync, system}`, each a number;
- `agents`: `[{label, count}]`, every agent label, most rows first;
- `actions`: `[{action, count}]`, every action with rows, most rows first;
- `projects`: `[{projectId, count}]`, every project with rows (as `projectId` counts them), most rows first; a deleted project keeps its id.

Each count is the rows that choosing that value lists, with the other filters kept: a facet ignores the filters its own choice replaces. Choosing a kind clears the agent, so the `actorKind` counts ignore both `actorKind` and `agent`; `agents` ignore `agent`, `actions` ignore `action` and `projects` ignore `projectId`. Later pages answer only `data` and `nextCursor`.

A cursor belongs to the filters of the page that gave it: with other filters it is refused with `validation_failed`, so a change of filters starts again from the first page. A cursor without filters, and a cursor written before these filters (with `entityType` and `entityId` alone), still page as before.

### T3 threads and sync

| Method and path       | Who   | Body                                                                                                           | Answer                                                                      |
| --------------------- | ----- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `POST /threads/start` | any   | `{threadId, parentThreadId (required, null for a top-level thread), title, projectId?, t3ProjectId?, itemId?}` | `{item: Item, created, linked}`: `201` when an item was created, else `200` |
| `POST /sync/t3`       | token | T3 snapshot (below)                                                                                            | `SyncResult`                                                                |
| `POST /sync/security` | token | Security snapshot (below)                                                                                      | `SyncResult`                                                                |
| `GET /sync/runs`      | any   | `limit?` (default 20)                                                                                          | `SyncRun[]`, newest first                                                   |

**Start of thread**, in one transaction: refuses `not_top_level` when `parentThreadId` is set; returns the item already linked to `threadId` (also on a retry or a race); otherwise links `itemId`, or creates a `task` in `projectId`, or in the project whose `t3ProjectId` matches, or in the inbox. The item is set `in_progress` (a closed item reopens). `suppressed` when the owner deleted this thread's item; `conflict` when `itemId` differs from the item the thread is linked to.

**Sync routes** accept a bearer token only (a browser session is `forbidden`). Changes are recorded with actor kind `sync`. Per-record failures are collected in `errors` (`record` is `project:<t3ProjectId>`, `thread:<threadId>`, `item:<id>`, `repo:<owner/name>` or `threads:<t3ProjectId>`; `code` is an error code) and never stop the run; `outcome` is `partial` when some failed or the snapshot lists `failedProjects`, `failed` when all failed.

T3 snapshot, a full read of every top-level and child thread of every T3 project, never a delta:

```text
{
  collectedAt,
  projects: [ {t3ProjectId, title, repo?: "owner/name" | null} ],
  threads:  [ {threadId, t3ProjectId | null, title, status, settled, settledAt?: time | null,
               parentThreadId?: id | null, updatedAt} ],
  failedProjects?: [ t3ProjectId ]
}
```

- `failedProjects`: T3 projects whose threads the sync tool could not read in this run, or read only in part (invalid thread records). Each is recorded in `errors` as `{record: "threads:<t3ProjectId>", code: "threads_not_read"}`, the run is `partial`, and no item of those projects (by its project or by a link's `t3ProjectId`) is decided in this run (`counts.itemsNotDecided`).

- Projects: created by `t3ProjectId` with the redacted title as name, `stage: null` and the repository; an existing project keeps its name and only gets a repository when it has none; a suppressed project id is skipped.
- A thread with a `parentThreadId` never gets an item. When it is linked, the link moves to its top-level thread (the parent's parent, as far as the snapshot knows): deleted when that thread has its own link, re-pointed otherwise.
- A top-level thread without an item and without a suppression (of the thread or its project) gets a `task` titled from the redacted thread title, in the mapped project or the inbox: when unsettled, whatever its age (`waiting` → `waiting_on_you`, otherwise `in_progress`); when settled, only if it settled (`settledAt`, else `updatedAt`) at most 7 days before `collectedAt` (status `done`). Items created by the first successful run are `imported`.
- Every link is refreshed (title, status, settled, `updatedAt` as last activity) when the record's `updatedAt` is newer than the stored last activity (an older or equal record is ignored, so snapshots applied out of order never roll back), then every item with a link is decided over all its links: any `running`, `starting`, `queued` or `preparing` → `in_progress`; otherwise any `waiting` → `waiting_on_you`; otherwise all settled → `done`; otherwise no change. The sync never moves an item out of `done` or `not_relevant`, never sets `done` on `future` or `todo`, and leaves a status the owner set at or after the threads' latest activity. Each change is a compare-and-set on the version read in that run; a changed or deleted item is skipped (`counts.itemsSkipped`) and decided again next run.
- Counts: `projectsCreated`, `projectsUpdated`, `projectsSuppressed`, `childLinksFolded`, `threadsUpdated`, `threadsSuppressed`, `threadsTooOld`, `itemsCreated`, `itemsUpdated`, `itemsSkipped`, `itemsNotDecided` (only the non-zero ones are present).

Security snapshot, from the `overview` collector:

```text
{
  collectedAt,
  repos: [ {repo: "owner/name", openIssues: n | null, issuesAsOf: time | null,
            families: [ {family, coverage, counts: {critical, high, medium, low}, asOf: time | null} ]} ]
}
```

Each repository is matched to every project whose `githubRepo` equals it, ignoring case (`counts.reposUnmatched` otherwise). The project's open Issues count and its time are replaced; each listed family is upserted; families not listed keep their last values. A family, or the open Issues count, whose as-of time is older than the stored one is ignored. `asOf` is the source's last success, not the sync time. An unchanged project writes nothing.

### Telegram

The bot and the morning message run inside the server, never through this API. They are on only while a bot token and a chat id are both in effect: each is set in Settings, or by `MIKUD_TELEGRAM_BOT_TOKEN` and `MIKUD_TELEGRAM_CHAT_ID`, which override the stored value per field. With one of them the state is `incomplete` and the bot stays off. A save restarts them; the morning message still goes out at most once a day.

**TelegramStatus**:

```text
{
  configured,          // a bot token and a chat id are in effect, and the bot runs
  polling,             // the bot's latest getUpdates call succeeded (false when not configured)
  lastUpdateAt,        // when the bot last recorded an update from any chat, or null
  lastMorning: {localDate: "YYYY-MM-DD", state, at} | null   // the latest morning run
}
```

- `lastMorning.state`: `sending` (in progress), `sent`, `failed` (Telegram refused it with a 4xx answer, or there was no connection; retried every 30 seconds until 11:00), `unknown` (it may have gone out: a timeout, a dropped connection, a 5xx or an answer that is not Telegram's, or a restart during the send; never resent) or `skipped` (11:00 passed without a send). `at` is the time of the latest state change.
- **Quick add**: plain text from the owner's chat becomes an inbox item exactly like `POST /capture` (type `idea`, status `future`), created by actor kind `bot` with audit source `telegram`. The bot answers with a link to `<MIKUD_PUBLIC_URL>/items/<id>`. Text that looks like a secret is refused as agent text is, and the bot answers that nothing was saved without repeating the text. `/start`, `/help` and other commands answer with a help text; photos and other non-text messages with a short note. Other chats get no answer.
- **Morning message**: 08:00 Asia/Jerusalem, Sunday to Friday, in the language of the settings, built from the overview's read (above) with `since` set to the owner's last visit on any device or the last morning message, whichever is later. Deep links: `<MIKUD_PUBLIC_URL>/` and `<MIKUD_PUBLIC_URL>/items/<id>`.
- **Test message**: `POST /telegram/test-message` (Settings, "Send a test morning message") builds the same message the job would send now and sends it to the owner's chat at once. It never reads or writes `job_runs`, so the 08:00 message still goes out, and it records two audit rows (action `telegram.test_message`): `after: {state: "sending"}`, committed before the send, then `after: {state, code?}` with `sent`, `failed` or `uncertain` and the failure code. Not retried.
