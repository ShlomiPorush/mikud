# AGENTS.md

## Project

Adiutor is a personal, single-user project-focus system: an overview board, a Telegram morning message and an MCP server that AI agents use to keep work items current. One application container with PostgreSQL, reachable only over the owner's private network.

**Stage: foundation.** Read these before any change:

- Product requirements: `docs/requirements.md`
- Foundation plan, decisions and status: `docs/project-foundation.md`

The foundation plan is the desired state. Items marked planned do not exist yet. Check the repository before assuming a file, command or feature exists.

UI follows the `v3-ui-style` skill.

## Layout

One pnpm package (no workspace apps).

- `src/server/`: Hono server. `index.ts` starts it and applies the owner's settings (the bot and the morning job when Telegram is on), `config.ts` reads and checks the environment (keys, wiring, the per-field overrides of owner settings; refuses `BETTER_AUTH_*`, `AUTH_SECRET` and the removed `ADIUTOR_AUTH_SECRET`), `cli.ts` is the recovery command (`reset-password`), `app.ts` mounts `/healthz`, Better Auth's own handler at `/api/auth`, `/api/setup`, `/api/v1`, `/mcp` and the built UI (`web.ts`: `dist/web` with a page fallback and the Content-Security-Policy) and maps errors, `healthcheck.ts` is the container health check, `errors.ts` holds the stable error codes, `db/` the Drizzle schema and client.
  - `auth/`: `auth.ts` (Better Auth 1.7.15 as it documents itself: the username, twoFactor and `@better-auth/api-key` plugins and the core `deviceAuthorization` and `bearer` plugins for agent approval, one `hooks.before` with the route allow-list, the `Authorization` allow-list (`BEARER_PATHS`) and the refusals, one `hooks.after` for sign-out, `databaseHooks` for the audit, and `AuthHolder`, which rebuilds the instance when a setting it reads changes), `recovery.ts` (the CLI's documented password reset).
  - `services/`: every write and read model. `context.ts` (actor, audit row, agent secret check, the link lock), `account.ts` (whether the owner exists), `items.ts`, `projects.ts`, `notes.ts` (notes and their versions: edits and restores at the version the writer saw, owner-only restore and delete, list pages by a cursor bound to its filters), `threads.ts` (start of thread), `sync.ts` and `sync-rules.ts` (T3 and security snapshots), `reads.ts` (morning, project, item, archive, inbox, and the audit log with its filters and facet counts, one `auditConditions` for the list and every count), `admin.ts` (settings with their environment locks, suppressions, visits), `secrets.ts` (the secret check, reloadable private domains).
  - `settings/`: `crypto.ts` (secrets stored in Settings, encrypted with `ADIUTOR_SETTINGS_KEYS`), `effective.ts` (each owner setting from the environment, the database or its default, and whether it is locked), `runtime.ts` (applies a save to the Better Auth instance, the bot and the secret check without a restart).
  - `http/`: `auth.ts` (an agent key through `verifyApiKey`, or a Better Auth session of an account with two-factor on, read from the cookie alone (`cookieOnly`); the CSRF check, the failed-key limit), `setup.ts` (`GET /api/setup/status`) and `api.ts` (the `/api/v1` routes). `mcp/server.ts`: the MCP tools.
  - `telegram/`: `api.ts` (Bot API client; a failure is `answer`, `not_sent`, `uncertain` or `aborted`), `html.ts` (Telegram HTML that escapes every value), `bot.ts` (long polling, one transaction per update), `runtime.ts` (owns the bot and the morning job; `reload` restarts them with the pair in effect, and sends sign-in codes), `texts.ts` (locale texts), `status.ts` (the status route's read).
  - `jobs/`: `morning.ts` (the 08:00 schedule and its durable runs in `job_runs`), `morning-message.ts` (the message, a pure function), `time.ts` (Asia/Jerusalem wall clock and number formats).
  - `testing/db.ts`: a migrated database per integration test file, and a movable clock. `testing/app.ts` (the app's core with Better Auth, the settings runtime and an idle Telegram service; agent keys and a signed-in owner for tests), `testing/browser.ts` (a cookie-jar browser with sign-up, enrolment and sign-in on Better Auth's routes), `testing/totp.ts` (a self-written RFC 6238 TOTP). `testing/bot-api.ts`: a stand-in Telegram Bot API on `127.0.0.1` for tests (getUpdates with Telegram's offset rules, sendMessage recorded, failures on demand).
- `src/shared/`: enum codes as `const` arrays with zod schemas (`enums.ts`), the API request schemas (`api.ts`, with the audit filters `auditFilterSchema` that the Activity page's address also uses), the activity search in words (`audit-search.ts`: the labels of a language mapped to the codes of `AUDIT_ACTIONS` and `AUDIT_ENTITY_TYPES` in `enums.ts`), the username and password rules and the session clock limits (`auth.ts`), the Date Format and Time Format settings that the UI and the morning message share (`datetime-formats.ts`), the default of each owner setting, which the schema's column defaults and Settings' Reset to default share (`settings.ts`), the UI paths that messages link to (`routes.ts`) and the locale files `locales/en.json` and `locales/he.json`.
- `drizzle/`: generated SQL migrations and their snapshots. Never edit by hand. The one exception is a data-only change: `pnpm db:generate --custom --name <change>` (documented by drizzle-kit) makes an empty migration whose SQL is written by hand (`0005_end-sessions`). No other hand-written SQL is allowed.
- `config/`: TypeScript base config, Vitest configs, Drizzle Kit config, `vite.config.ts` (the UI build) and `playwright.config.ts` (end-to-end tests).
- `docker/`: toolchain and application Dockerfiles, the development Compose template and `dev.env.example` (the example of `.env.dev`, every line commented out).
- `scripts/`: `local.sh`, `verify.sh`, `try-pr.sh`, `release.sh` and its tests `test-release.sh`, `ci-result.sh` (the CI run a release reuses) and its tests `test-ci-result.sh`, `test-release-workflow.sh` (the Release workflow's wiring), `test-try-pr.sh` (the address, ports and proxy `try-pr.sh` generates, and its `status`); `lib/common.sh` (shared helpers), `lib/guards.sh` (repository guards) and `lib/try-pr-seed.mjs` (the owner, an agent key and invented fixtures for `try-pr.sh`).
- `src/sync/`: the sync tool that runs on the owner's PC, bundled to `dist/sync/adiutor-sync.js` (Node stdlib only at runtime; no imports from `src/server/`). `main.ts` is the entry, `run.ts` one run, `connect.ts` the `connect` command (agent approval: device code, one key, the session ended in a `finally`, the env file restricted with `icacls` or mode 0600), `fixtures/` invented T3 and `overview` data for its tests. See `docs/sync.md`.
- `prompts/`: `reconcile.md`, the instructions of the T3 scheduled task that runs the sync tool.
- `skill/`: the agent skill. `adiutor/` is the folder the shared agent configuration installs for Claude Code and Codex: `SKILL.md` (the agent instruction: when and what agents write in Adiutor, each MCP tool next to its command) and `scripts/` with the `adiutor` command in three versions with one contract (`adiutor.mjs` for Node 20+, standard library only; `adiutor.ps1` for Windows PowerShell 5.1 and PowerShell 7; `adiutor.sh` for POSIX sh and curl) and the `adiutor` sh launcher (Node 20+ unless `ADIUTOR_NO_NODE`, else PowerShell on Windows or `adiutor.sh`). The command connects through agent approval like `adiutor connect` of the sync (one key, the session revoked at once), keeps the connection in `~/.adiutor/` (`ADIUTOR_SKILL_HOME`), and calls only the fifteen `/api/v1` routes of the MCP tools. `test/`: `contract.test.mjs` (node:test, per version: `ADIUTOR_IMPLS`, a version whose file is missing is skipped) against `fake-server.mjs`, a stand-in for Better Auth's approval routes and `/api/v1`. Imports nothing from `src/`.
- `docs/api.md`: the HTTP API and MCP contract. Change it together with the routes.
- `docs/deployment.md`: the owner's deployment notes. `.github/workflows/`: `ci.yml` and `release.yml`.
- `src/web/`: the web UI (React 19, Vite, React Router, TanStack Query), built to `dist/web`. Its own `tsconfig.json` (DOM, JSX).
  - `api/`: `types.ts` (every shape of `docs/api.md`), `endpoints.ts` (every `/api/v1` route and the query keys), `client.ts` (the one fetch client: CSRF header, `{error}` to `ApiError`, 401 and `totp_required` to the app), `auth.ts` (Better Auth's React client with the twoFactor, username and api-key plugins, and its failures). `mock/`: invented data behind the same routes (`mock/auth.ts` answers Better Auth's), loaded only with `VITE_ADIUTOR_MOCK=1`; `adiutor.mock.env` in localStorage (variable names, comma separated) locks those settings as the environment would, and `adiutor.mock.telegram` set to `off` starts with Telegram off.
  - `ui/`: the shared builders and parts: `Markdown.tsx` (a note body through react-markdown: no raw HTML, its own URL check, each block in its own direction), `Dialog.tsx` (every dialog; a sheet on phones), `Menu.tsx` (every menu, a layer of `layers.ts`), `Picker.tsx` (every picker: a listbox with a search above ten choices, or the panel of `SortButton.tsx`, the one Sort button of a list; a layer of `layers.ts`), `FilterBar.tsx` (the filter bar: a search that waits for a pause, the Filters button with its count, the count line with Clear filters, and the return to the first row on new filters; not a layer), `Toast.tsx`, `confirm.tsx`, `layers.ts` (Escape, Back, focus, inert), `unsaved.tsx` (save bar guard), `refresh.ts` (`usePageQuery`, the paces), states, tags, time, copy.
  - `shell/`: the frame copied from n8n-ops' Regular shell (`Shell.tsx`: top bar, sidebar that folds into the rail, phone bars, More sheet), `ShellTools.tsx` (the fold toggle, the theme button, the account menu with the theme, Account and sign-out, the T3 sync card), `chrome.tsx` (`PageHead` and `PageActions`: a page's actions move into the top bar from 761px; the h1 is the top bar's there and the page's own on a phone), `navFold.ts` (`adiutor.nav`, applied by `public/boot.js`), `signOut.ts` (the unsaved question, then Better Auth's `signOut`), the bell, quick add, item actions with Undo, theme, the session gate with Better Auth's `useSession` (`Root.tsx`). `pages/`: one file per page and the item dialog; `pages/auth/` the sign-in and setup pages outside the gate (with the backup codes) and `ConnectDevicePage.tsx` (`/connect/device`, the agent approval: inside the gate, outside the frame); `AccountPage.tsx` the Account page (`/account`, from the account menu: the signed-in browsers, the password, two-factor and recovery, all Better Auth's routes, outside Settings and its draft); `pages/settings/` the section catalogue (`sections.ts`: groups, `/settings/<section>`, the field of the one draft to its section, a refused field from the server's details), the Agent access and Sync sections and the group and row parts; `SettingsPage.tsx` holds the one draft and the General, Telegram and Secret check sections. `format/`: the only date, time and number helpers. `i18n/`: locale lookup with plurals. `styles/ui.css`: the one stylesheet of `--ui-*` tokens and `ui-` components.
  - `guards.test.ts`: the v3 guards (popups only from the builders, every page refreshes, dates through the helpers, locale keys used exist).
- `e2e/`: Playwright specs against a running Adiutor, desktop then phone (each with its own `X-Forwarded-For`): `auth.spec.ts` (first-run setup with TOTP and backup codes, a wrong password, sign-in, sign-out, a backup-code sign-in) runs first and stores each project's signed-in browser; `session.spec.ts` (Better Auth's client extends the session when the tab comes back, through the transport fix, and Adiutor's polling alone does not; needs `E2E_DATABASE_URL`, which `verify.sh` sets), `connect.spec.ts` (`dist/sync/adiutor-sync.js connect` run as a child process and approved or denied by Playwright, the key saved and then disconnected, the page in English and signed out), `filters.spec.ts` (the Activity filters: Who with the server's counts, the address through a reload, Back and Forward, a project and a Hebrew search, Clear filters, the Filters button by keyboard, the phone's layout, and All activity from the item dialog with an unsaved comment), `picker.spec.ts` (the Projects Sort button with its headers, the phone's stage picker, moving an inbox item with the picker and Undo, the item dialog's project picker with Escape and Back), `settings.spec.ts` (how to connect, the password, the Telegram fields), `skill.spec.ts` (the agent skill's `adiutor.mjs` connected through `/connect/device`, no leftover approval session, then a thread's item, a comment and a note as `agent:<label>` in the activity log), `shell.spec.ts` (one h1 per page, the folded sidebar after a reload, the width boundaries, the theme with System, the account menu and More on Escape and Back) and `ui.spec.ts` (morning, an item status change with Undo, quick add, sign-out from the account menu with Stay and a failed sign-out) reuse it. `helpers.ts` and `totp.ts` hold the shared state and the codes.

## Commands

Run every script inside WSL from the repository. Node, pnpm, shellcheck and shfmt run in the toolchain container; the host needs Docker only.

- `scripts/verify.sh`: guards, Biome, types, unit tests, the agent skill's contract tests (`pnpm test:skill` in the toolchain, then the node version again in `SKILL_NODE_IMAGE`, a pinned Node 20 image), build, schema-versus-migration check, database tests against a disposable PostgreSQL 16 (`adiutor-verify`, `TEST_POSTGRES_IMAGE`; it stops unless the server reports 16), then the image with health, UID and hardening checks, then the end-to-end tests in the Playwright image against that container. After the build it checks `dist/web` for external assets and the mock (`scripts/lib/web-dist-check.sh`). `--guards-only` for the guards alone; `--changed [BASE]` runs guards only when every change is documentation; `--skip-e2e` skips the end-to-end tests.
- `scripts/local.sh build|up|start|down|status|logs|nuke`: the development stack (`adiutor-dev`) from the ignored `docker-compose-dev.yml`. Create it once with `cp docker/docker-compose-dev.example.yml docker-compose-dev.yml`. Serves `http://127.0.0.1:8090`; `ADIUTOR_PORT` changes the port and `ADIUTOR_PUBLIC_URL` the address the browser opens (a reverse proxy; both may be set in `.env.dev`). `up` and `start` generate the database password and the keys once into `<data dir>/stack.env` (0600) and refuse a database whose `stack.env` is missing.
- `scripts/try-pr.sh <number>|status|restore`: runs a pull request's head as the separate Compose project `adiutor-pr` (own PostgreSQL 16, generated keys in a 0600 file under `~/.cache/adiutor/try-pr`, an owner created through Better Auth's sign-up with a generated password, TOTP secret, backup codes and an agent key in `owner.env` there, also 0600, Telegram off, invented fixtures) on `http://pr.localhost:8091`; `ADIUTOR_PR_PORT` changes the port. Its server publishes no port: an nginx proxy (`proxy.conf` there) publishes `127.0.0.1:8091` and passes it only requests for the host `pr.localhost` (421 for any other), so the browser never sends it the cookies of `127.0.0.1`, where the development stack runs. Agents are not connected to a pull request stack: `connect` and the skill accept plain http only for `localhost` and `127.0.0.1`, and Node does not resolve `pr.localhost` (browsers and curl do). Never touches `adiutor-dev`. `restore` removes the stack, its data, image and worktree.
- Recovery on a running stack: `docker compose exec adiutor node dist/server/cli.js reset-password` (production) or `source scripts/lib/common.sh && dev_compose exec adiutor node dist/server/cli.js reset-password` (development). It runs Better Auth's documented reset: prints a new password once and ends every session; two-factor stays.
- Releases: the **Release** workflow (Actions → Release → Run workflow on `main`, choose patch, minor or major; `dry_run` checks everything and publishes nothing) reuses the newest CI run of the commit on `main` when its latest attempt succeeded (waiting up to 30 minutes for one that still runs; it never falls back to an older green run) and runs the whole CI on the commit otherwise (`scripts/ci-result.sh` decides, and the workflow checks a reused run again with it right before `release.sh`), then `scripts/release.sh --target ghcr --bump <patch|minor|major> [--dry-run]`: release commit and tag, the image on GHCR (the version, then `:latest`) and the GitHub Release from the CHANGELOG section. A run that stopped halfway is finished by the next run (a new Run workflow, not "Re-run failed jobs"). Agents never release: they run the workflow only with `dry_run`, and `release.sh` only with `--dry-run`. `scripts/test-release.sh` (run by the guards) covers each way a run can stop, `scripts/test-ci-result.sh` which CI run counts, and `scripts/test-release-workflow.sh` which jobs and steps run on both CI paths with and without `dry_run` (both also run by the guards). Never deploys.
- A single tool in the toolchain: `source scripts/lib/common.sh && build_toolchain && in_toolchain "pnpm test"`.
- The agent skill's contract tests alone: `in_toolchain "pnpm test:skill"` (node and sh), or `node --test skill/test/contract.test.mjs` with any Node 20+ on the host (on Windows: node, ps and pwsh; `ADIUTOR_TEST_TMP` moves the temporary folder). `ADIUTOR_IMPLS=node,sh` picks the versions.
- UI development: `in_toolchain "VITE_ADIUTOR_MOCK=1 pnpm dev:web"` serves the UI on the mock API (port 5173 in the container); without the flag `pnpm dev:web` proxies `/api` to the development stack.
- End-to-end tests against the development stack: `docker run --rm --ipc=host --network host --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD:/repo" -w /repo mcr.microsoft.com/playwright:v1.65.0-noble npx playwright test --config config/playwright.config.ts` (from a WSL clone; the tests create invented records and set the language to Hebrew). Pass `-e E2E_USERNAME -e E2E_PASSWORD` (the run refuses to start without a password), and `-e E2E_TOTP_SECRET` when that owner exists; on an empty database the first test creates the owner with them. Only `scripts/verify.sh`, whose stack is thrown away, lets global setup make a new password for the run.
- New migration after a schema change: `in_toolchain "pnpm db:generate --name <change>"`. `verify.sh` fails when the schema and the migrations disagree. A data-only change uses `pnpm db:generate --custom --name <change>` and is the only hand-written SQL.

Verify in proportion to the risk of the change, and report what ran and its result:

- **Documentation only** (`docs/`, `README.md`, `AGENTS.md`, `CHANGELOG.md`, `LICENSE`; nothing under `prompts/`, whose `reconcile.md` instructs the T3 scheduled task): `scripts/verify.sh --changed`, which then runs only the guards.
- **Anything else**: the full `scripts/verify.sh` before opening the pull request.

On a pull request, CI runs the guards, and `scripts/verify.sh --changed origin/main` unless only Markdown files, `docs/` or `LICENSE` changed; then it runs only the guards.

## Traps

- Node 25 and later no longer ship Corepack. Both Dockerfiles install it from npm at a pinned version (`corepack@0.36.0`) before `corepack enable`; the toolchain's `corepack prepare pnpm@...` must name the version of `packageManager`.
- The sync bundle (`build:sync`) targets `node24`, the Node of the owner's PC, while the server targets `node26`. Move the sync target only after the PC runs a newer Node (see `docs/sync.md`).
- pnpm 12 reads its settings only from `pnpm-workspace.yaml` (not from `package.json`), and refuses to install when a dependency's build script is not allowed there. The file holds settings only; it lists no packages.
- `grep -P` with `\x{...}` code points needs a UTF-8 locale; `scripts/lib/guards.sh` sets `LC_ALL=C.UTF-8` and stops on any grep error, so a broken pattern cannot pass silently.
- Tests named `*.integration.test.ts` run only from `verify.sh`, which passes `ADIUTOR_TEST_DATABASE_URL`. `pnpm test` skips them.
- UI component tests are `*.test.tsx` with `// @vitest-environment happy-dom` on their first line; `pnpm test` runs them in that DOM with the other unit tests.
- Node refuses to start a `.cmd` file (the T3 CLI on Windows) without a shell. `src/sync/exec.ts` runs it through `cmd.exe /d /v:off /s /c` with every part quoted and refuses `"`, `%` and line breaks; never build a shell string anywhere else.
- Production runs PostgreSQL 16. No setting, function or syntax newer than 16 (`transaction_timeout` is 17 or newer and made v0.1.0 fail at its first query). `verify.sh` and `try-pr.sh` run `TEST_POSTGRES_IMAGE` (`scripts/lib/common.sh`, PostgreSQL 16, data in `/var/lib/postgresql/data`); the development stack stays on 18, so a dump of it does not restore into 16.
- "New since your last visit" belongs to the owner's account: `visits` names no browser. The pool bounds each statement and idle time in a transaction, not a whole transaction (`db/client.ts`); keep the app's transactions short.
- `ON DELETE RESTRICT` (items and notes of a project) fails with SQLSTATE `23503` on PostgreSQL 16, which production and `verify.sh` run, and `23001` on 18 (the development stack). The services never rely on either: `deleteProject` refuses with `conflict` while a project has items or notes.
- Codes are text columns with database checks generated from `src/shared/enums.ts`: adding a code needs a new migration.
- A new audit action goes into `AUDIT_ACTIONS` (`src/shared/enums.ts`) with a label in `audit.action` of both locale files (`audit-search.test.ts` fails otherwise); no database check uses that list. Activity counts come from `auditConditions` in `services/reads.ts`, never from rows the UI loaded.
- Services take their time from `ctx.clock()`, never `now()` in SQL or `new Date()`, so tests can move time; integration tests use `createTestDatabase` from `src/server/testing/db.ts`.
- Exported service functions are `async`: a refusal must be a rejected promise, not a synchronous throw.
- A credential a test, the end-to-end run or the mock API hands to something that accepts it (a password, an auth secret, a settings key, a bot token, an agent key, a session, a database URL with a password) is new on every run: `src/server/testing/secrets.ts` on the server, `node:crypto` or `crypto.randomUUID()` elsewhere. One value per test file or scenario when several consumers must agree on it. Literal values are only samples the secret check must find and values a test expects to be refused; assemble them at run time (`${"gh"}p_...`), and private IPv4 addresses with `[10, 1, 2, 3].join(".")`: the guards and GitHub push protection scan the literal text. The mock API holds no password and accepts any that is not empty.
- Telegram is off unless a bot token and a chat id are both in effect (Settings, or `ADIUTOR_TELEGRAM_BOT_TOKEN` and `ADIUTOR_TELEGRAM_CHAT_ID`, each overriding its field). Tests never reach the real Bot API: they start `StandInBotApi` (`src/server/testing/bot-api.ts`) and give its URL to `BotApi`. `TELEGRAM_API_URL` exists for the same purpose and stays empty in production. The token is part of every Bot API path: never log a URL, a fetch error's message or message text; log `TelegramError.code`.
- The morning message goes out at most once a day: its `job_runs` row is taken as `sending` before the send. Only a definite failure (`answer`, `not_sent`) becomes `failed` and is retried; anything else becomes `unknown` and is never resent. Do not add a resend path for `unknown`.
- Bot text goes through the same secret check as agent text: `checkAgentText` covers actor kinds `agent` and `bot`.
- Write bidirectional control characters in source as escapes (backslash, `u`, four hex digits), never as literal characters. Some editing tools turn the escapes into the characters; check new files before committing.
- UI text keys may not contain dots inside one segment: the lookup splits keys on `.`, so audit actions are keyed `item_update`, not `item.update`. Hebrew is allowed only in `he.json`: a language's name written in that language comes from `Intl.DisplayNames`, not from `en.json`.
- The production UI build defines `__ADIUTOR_MOCK__` as `false`, which drops `src/web/api/mock`; `web-dist-check.sh` fails when the mock's storage key `adiutor.mock.` is in `dist/web`. Never import the mock any other way.
- `@playwright/test` in `package.json` and `PLAYWRIGHT_IMAGE` in `scripts/lib/common.sh` must name the same version; `verify.sh` refuses a mismatch.
- The verification stack's `ADIUTOR_PUBLIC_URL` is `http://127.0.0.1:8090` (set by `verify.sh`); the server refuses a browser change whose `Origin` differs. `e2e/global-setup.ts` forwards that address to the container (`E2E_TARGET`), so do not point the tests at `http://adiutor:8080` directly.
- The UI formats dates only through `src/web/format/datetime.ts` (app time zone Asia/Jerusalem, the Date and Time Format settings); `guards.test.ts` fails on `toLocaleDateString`, `Intl.DateTimeFormat` and the like anywhere else. Every layer comes from `ui/Dialog.tsx` or a builder listed there with its reason.
- A layer portals its root element straight into `document.body` and passes it to `openLayer` from an effect that reads the element's ref. Never create, append or remove a layer element outside React: `main.tsx` turns on StrictMode, which in development runs every effect, its cleanup and the effect again, and a root removed by that cleanup leaves the layer empty. For the same reason a closed layer gives its history entry back in a microtask, so a layer that opens in the same synchronous run keeps it (StrictMode's second run, or a synchronous swap of one layer for another). Not covered, as before: a layer opened from a later microtask or task after another closed gets no entry of its own, and a Back that races a close can go one step too far. `ui/layers.test.tsx` renders the dialog, the bell window, the More sheet and the toast under StrictMode.
- The guards scan tracked files and new files that are not ignored. The deny list `docs/private/deny-list.txt` exists only on the owner's machine; in CI the guard is skipped, and its output never repeats a matched line.

- **Better Auth is used only as it documents itself.** Its built-in features, options, official plugins and documented hooks; never a wrapper around its handler, a lock around its requests, Adiutor session clocks or proofs, or post-processing of its answers. A requirement those cannot meet is a gap for the owner (see "Security design" in the foundation plan), not code. Put this rule in a reviewer's prompt.
- **The route allow-list lives in `hooks.before` (`ALLOWED_PATHS` in `auth/auth.ts`), matched on `ctx.path` (the route pattern) for HTTP requests only.** A new Better Auth route stays closed until it is listed; `auth/auth.test.ts` fails when a listed path no longer exists. Server calls (`auth.api.*`) have no `ctx.request` and pass.
- **Better Auth names the authenticator account after the e-mail** and has no option for it. `TotpStep` passes Better Auth's `totpURI` through `authenticatorUri` (`src/shared/auth.ts`), which drops `@adiutor.local` from the label only, before the QR code is drawn (owner's decision, 2026-11-03). Never change the query or the secret there; remove it when Better Auth gets an option for the account name.
- **Better Auth cannot require two-factor.** The `/api/v1` middleware and `/api/setup/status` accept a session only while `user.twoFactorEnabled` is true; the setup page calls `revokeOtherSessions` after enrolment. A parallel sign-in during enrolment can keep a session (G6); the test pins the gap. Replacing the authenticator turns two-factor off until the new one is verified, so the password alone signs in meanwhile (G-C; Better Auth has no staged rotation); its test pins it too. Do not "fix" either with custom session code or a custom rotation.
- **`deferSessionRefresh`: only the Better Auth client's own refresh extends a session.** Keep `sessionOptions.refetchInterval` at 0, and never call the client's `getSession` or `useSession().refetch` from background polling: that would keep any open tab signed in for ever.
- **Sign-out audit never throws.** Better Auth swallows a throwing `session.delete.before` on `/sign-out`, answers 200 and leaves the session valid. Sign-out is audited in `hooks.after`, which logs and never throws. Every other audit hook may refuse by throwing.
- **Hook order:** the user's `hooks.after` runs before the plugins' after-hooks, so the sign-in audit lives in `databaseHooks.session.create.before`, keyed on `context.path`. `databaseHooks` do not fire for the api-key plugin's model: key events are audited in `hooks.before`.
- **Audit rows go through Adiutor's own connection**, not Better Auth's transaction (its transaction-scoped adapter is not documented). A row can outlive a change that rolled back (G5).
- **`bearer()` makes a session token usable as `Authorization: Bearer` on every Better Auth route.** The `hooks.before` refuses the header everywhere but `BEARER_PATHS` (`/api-key/create`, and `/revoke-session` of the bearer's own token), with or without a cookie; it runs before the plugin's hook and reads the raw header. Adiutor's own routes pass `cookieOnly(headers)` to `getSession`, never the request's headers. Do not widen either (G10, G-B). The allow-list does not cover the rest of G10, accepted by the owner (2026-11-02): `bearer()` also hands page script the signed session cookie in `set-auth-token`, which works as the cookie; do not strip or rewrite it, keep its regression test, and keep the Content-Security-Policy at `script-src 'self'`.
- **The api-key plugin's list answers at most 100 keys** (the adapter's default limit). Settings shows that list as it is; Disconnect all (`pages/settings/disconnectAll.ts`) lists and deletes until a list is empty.
- **The agent skill's three versions keep one contract.** `adiutor.mjs`, `adiutor.ps1` and `adiutor.sh` read and write the same files (`connection`, `pending`, `left`: one line of flat JSON per record, no quote, backslash or control character in a value) and the same lock file (`lock`, created exclusively: token, host, process id and that process's start time, compared exactly; a certainly dead holder's lock is removed only by the holder of `lock.break`, created exclusively the same way, and only while the lock still names that dead holder; nobody removes a `lock.break` automatically, and `busy` names one left behind, like an undecidable lock; the holder checks it is still its own before every one-time request and every file change). Every save is conditional on the files exactly as read under the lock. Temporary files are `<file>.<12 hex>.tmp`, and the next holder of the lock removes any a stopped command left. A change to a file, an error code or an answer goes into every version and its contract test. The session token from `/device/token` never reaches a file, an argument, a child's environment or the output in any version. `adiutor.sh` unsets every name it assigns at start-up (an exported name would hand its value to every child); the contract test reads the script and fails on a name missing there. Every file under `skill/` is printable ASCII (a guard).
- **Agent approval:** `validateClient` accepts only `adiutor-connect`; `GET /device` claims a code and Better Auth limits it to 5 per 10 minutes per address, so `/connect/device` reads it once and never polls. `/revoke-session` is audited in `hooks.after` and never throws: a refused revoke would leave the device session alive. The device session's lifetime is the session's `expiresIn` (the idle days); there is no option of its own.
- **The api-key plugin limits each key to 10 requests a day by default.** Adiutor sets `rateLimit: { enabled: false }`; keep it, or the sync stops. `enableSessionForAPIKeys` stays false: a key never becomes a session.
- **`trustedProxies` holds only behind Traefik**, with Adiutor reachable through Traefik alone and Traefik replacing client forwarding headers (deployment.md). In the dev and verify stacks there is no proxy: tests and e2e projects send their own `X-Forwarded-For` (a valid address, one per browser), or every request shares one bucket. Adiutor's failed-key limit (`clientAddress` in `http/auth.ts`) reads `X-Forwarded-For` only from a socket peer in that list, through Better Auth's `getIP`, so an entry means the same in both limits; it applies to requests with an `Authorization` header only. Under `NODE_ENV` test or development `getIP` answers `127.0.0.1` where production gets null, so in tests a peer that Better Auth reads as `127.0.0.1` is never a trusted proxy (another loopback address can be), and an unreadable header from a trusted peer gives `127.0.0.1` instead of the peer (`auth.test.ts` checks production in a child process).
- **The `/api/auth` mount passes a request without content with a null body (`withoutEmptyBody` in `app.ts`, owner's decision).** Better Auth's client sends its refresh `POST /get-session` without a body, `@hono/node-server` attaches an empty body stream to every POST, and better-call's `getBody` then answers 415 for a missing Content-Type. Only not GET or HEAD, `Content-Length: 0` and no `Transfer-Encoding` qualify; a real body keeps Better Auth's own checks. It normalizes the transport only; never extend it to Better Auth's options or answers. Remove it when upstream sends no body for empty requests (`e2e/session.spec.ts` and `auth-flow.integration.test.ts` cover it).
- **Better Auth skips its origin check under `NODE_ENV=test`**; `auth.ts` sets `advanced.disableOriginCheck: false` so tests see production's behaviour. Keep it.
- **`BETTER_AUTH_*` and `AUTH_SECRET` refuse to start:** Better Auth reads them on its own when an option is missing. `ADIUTOR_AUTH_SECRET` (Better Auth's single legacy `secret`, removed before the first release) refuses to start too, even when empty, so a value left behind never looks as if it still does something; the message never repeats the value.
- **Two key families:** `ADIUTOR_AUTH_SECRETS` (Better Auth's versioned `secrets`: cookies, TOTP and backup codes; no legacy `secret`) and `ADIUTOR_SETTINGS_KEYS` (secrets stored in Settings). Never share a value between them. Rotate by putting a new version first and keeping the old one listed.
- **The CLI reset never touches two-factor.** It runs `requestPasswordReset` with a local `sendResetPassword`, then `resetPassword`, as server calls; both routes stay closed over HTTP.
- **Owner settings:** every setting the owner manages lives in the `settings` row with a default and is edited in the UI. An environment variable may override one field; the API answers `setting_locked` and the UI shows the field locked with the variable. Only the database connection, file paths, deployment wiring and the keys stay in the environment alone.
- **Sign-in is rate limited** (5 per 5 minutes per address and route, also in tests). Integration tests give each browser its own `X-Forwarded-For`; end-to-end specs reuse the session stored by `auth.spec.ts` instead of signing in again, and `freshTotp` never sends a code of an already used 30-second step.

## Docker

- One image, `docker/adiutor.Dockerfile`: esbuild bundle and migrations on `node:26.13.0-bookworm-slim`, `USER node`, no `node_modules`, health check `node dist/server/healthcheck.js` (calls `/healthz`, which runs `select 1`). State lives only in PostgreSQL; the container has no volume and runs with a read-only root file system, no capabilities and `no-new-privileges`.
- `docker-compose.yml` (production) runs only `adiutor` from `ghcr.io/shlomiporush/adiutor:${VERSION}` behind Traefik on the external `traefik` network, with no published port and no database; `DATABASE_URL` in `.env` points at the owner's PostgreSQL. Interpolation is limited to `VERSION` and `DOMAIN`.
- `docker/docker-compose-dev.example.yml` adds a `postgres` service (PostgreSQL 18; `verify.sh` alone sets `ADIUTOR_POSTGRES_IMAGE` and `ADIUTOR_POSTGRES_DATA` to run `TEST_POSTGRES_IMAGE`, PostgreSQL 16, with its data path) with data in `${ADIUTOR_DATA_DIR}/postgres` (default `~/.local/share/adiutor-dev`, on the WSL file system; the scripts refuse a path under `/mnt`). `adiutor` publishes its port on every interface, for a reverse proxy. Both services read `<data dir>/stack.env`, which `scripts/lib/common.sh` (`ensure_stack_env`) generates once, before PostgreSQL first starts, and never rewrites; `adiutor` then reads the optional, ignored `.env.dev` at the repository root (Compose `env_file` with `required: false`), which `dev_compose` also passes as `--env-file` so `ADIUTOR_PORT` and `ADIUTOR_PUBLIC_URL` set there reach the template. Keys an older `.env.dev` sets keep winning; never remove them (the data they encrypted needs them). `scripts/verify.sh` generates new values per run in its temporary data directory and passes `--env-file /dev/null`, `ADIUTOR_LOCAL_ENV_FILE=/dev/null` and a fixed `ADIUTOR_PUBLIC_URL`, so it never reads `.env.dev`, and try-pr writes its own Compose file. Never read, copy or commit `.env.dev`. An existing `docker-compose-dev.yml` is a copy: copy the template again to get the change.
- Images are built only by the scripts; a guard fails on `build:` in a Compose file. Never stop or remove containers, networks or volumes of other projects.

## Repository policies

- The repository is public. Everything tracked is in English, except the Hebrew locale file `src/shared/locales/he.json`. Tests read Hebrew text from that file.
- Never commit environment-specific details: hostnames, IP addresses, bucket names, network details, tokens, real project names or real project data. They belong in the ignored `docs/private/` or in the server's `.env`. Fixtures and screenshots use invented projects.
- Store statuses, stages, types and severities as English codes; user-visible labels come from the locale files only.
- Keep the repository root minimal. Every root file is listed and justified in the foundation plan.
- Add user-visible or operational changes under `Unreleased` in `CHANGELOG.md`, written for the next release (no Changed or Fixed entries about things that were never released). Do not bump versions in pull requests; the Release workflow does that.
- Never commit `docs/private/`, `.env` or `docker-compose-dev.yml`. **No working value in the repository, not even a fake or dev-only one:** environment files are tracked only as examples (`*.example`) with secrets and `DATABASE_URL` empty; stacks generate their own (a guard fails otherwise).
- Kanzo (AGPL) inspired the idea. Never copy its code.
- Commit email is the GitHub noreply address.

## Product rules that code must enforce

- Agents may not delete items or projects and may not change a stage (they propose one). Only the owner, in the UI, does that.
- Every write goes through the services layer and writes an audit row in the same transaction. The one exception is the writes Better Auth does itself (sign-in, enrolment, sign-out), which fail closed instead (see Traps).
- The browser signs in with Better Auth and TOTP, which is mandatory. Agents and the sync use agent keys only (Settings, Agent access); a session never stands in for a key, and a key never becomes a session.
- Text written by agents and the Telegram bot is checked for secrets and refused with `secret_suspected`.
- The bot serves only the configured owner chat and never answers another chat.
- The server never calls T3 or GitHub. Their data arrives through the sync tool on the owner's PC.
- The sync never overrides the owner: see "Agent and sync rules" in the foundation plan.

## Out of scope for agents

- Production deployment is the owner's. Agents have no access to the production server; run Adiutor only on the local development stack.
- No backup feature: the owner backs up the database with his own tools.
